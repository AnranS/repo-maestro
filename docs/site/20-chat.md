# Chat with the orchestrator

The **chat** tab is your main interface. It is a provider-backed chat (`cursor` by default, with `codex` and `claude` available when configured) with two superpowers:

1. **System context** — every message you send is wrapped with the current workspace state: projects, run status, memory, and relevant skills.
2. **`maestro-action` blocks** — the assistant can emit structured YAML blocks that the dashboard renders as actionable buttons (`work`, `run`, `approve`, `status`, `rerun`, or `plan_validate`).

## Sessions

Each chat is a session persisted under `.maestro/chat/sessions/`. Cursor sessions also keep the provider chat id so they can resume. A session has:

- A title (auto-generated by the tagger model on first user message, editable)
- A list of free-form tags (auto-generated, editable)
- A pinned provider (optional — defaults to `MAESTRO_CHAT_PROVIDER`, then `.maestro/settings.yaml`, then `cursor`)
- A pinned model (optional — defaults to `defaults.agent_model`)

The sidebar shows all your sessions filterable by tag. The **+ new** button creates a fresh session; the trash icon deletes one (with confirmation).

## The system prelude

Before each user message is sent, `maestro` injects an invisible prelude built from:

```text
## Workspace
- workspace root: ~/work/login-demo
- projects: login-api (backend, python/fastapi), login-web (frontend, react/vite)

## Active run
- run id: 20260516-082011_d4c95577
- 2 tasks done, 0 running, 0 failed

## Recent decisions (L2, capped to 5/project)
- login-api / 20260515-110203: switched to bcrypt
- ...

## Action protocol
... (instructions on how to emit a small `maestro-action` block, usually `verb: work`)
```

This means the agent always knows the lay of the land without you having to repeat it.

## Continuation briefs

Use `maestro chat brief` to write a local handoff file for the current session:

```bash
maestro chat brief
maestro chat brief <session-id> --stdout
```

The brief is deterministic: it includes the latest compaction summary, recent messages, and pending/failed action cards. By default it is written to `.maestro/chat/continuations/<session>.brief.md`.

## Streaming

Assistant responses stream token-by-token over Server-Sent Events. While streaming you see:

- A blinking caret next to the assistant bubble
- Action blocks materializing as soon as their fenced YAML block closes
- A **stop** button to abort generation

If the same content arrives twice (some providers emit a final cumulative message after deltas), `maestro` dedupes silently using the provider's final result as the canonical text.

## Provider and model override per session

Bottom-left of the chat input has a **provider picker** and **model picker**. Choices:

- Provider default — use the configured chat provider
- `cursor`, `codex`, or `claude` — pinned to this session only
- Agent default model — omit `--model` and let the active provider choose
- Any cached/fallback model for the selected provider

The model list is grouped by provider when multiple providers are visible. Refreshing with a provider selected refreshes that provider's model list; refreshing with provider default refreshes the combined list.

## Auto-tagging

After your first user message, a cheap background task hits the **tagger model** (defaults to your `defaults.tagger_model`, falls back to `defaults.agent_model`) and proposes 1–3 tags for the session. You can edit them inline in the sidebar.

Why a separate model? Tagging on every message would burn money if you ran it on the same big model you use to chat. The tagger model is meant to be cheap (`gpt-5-mini`, `composer-2-fast`, etc.).

## Privacy

The tagger ONLY sees **user-side** messages — never your assistant output. This is enforced in `chat/tagger.rs`. If you don't want auto-tagging at all, set `defaults.tagger_model` to a non-existent id and the tagger will fail silently with no impact on the rest of the system.
